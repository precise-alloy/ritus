## Notes

- Design: the v2-vs-v3 round (`build.py round --show v2-vs-v3`): 23 scenarios in 13 groups x 2 arms x 3 runs = 138 runs, all collected and graded, with 348 judge verdicts from 17 blind bundles that mix both arms. Each assertion is an outcome (what the developer gets) or a process point (Ritus mechanics, several of them 3.0-only). The numbers below come from scores.md.
- Overall: outcome 427/441 (96.8%) for 3.0.0 vs 359/441 (81.4%) for 2.1.2; process 108/111 (97.3%) vs 55/111 (49.5%); mean per-run pass rate over all assertions 96.6% vs 76.7%. 3.0.0 is ahead on outcome in 11 of 13 groups and behind in 2 (checks-epic by 2 assertions, verify-probes by 1).
- Largest outcome gains: execute 51/51 vs 25/51, almost all from e1, where 2.1.2's execute-task stops BLOCKED on the stale formatCents step in 3/3 runs, and so fails 8 dependent assertions per run. plan-standard 42/42 vs 33/42: in r1 2.1.2 never pinned the refunded fee to half-up rounding nor carried the value rules into the task files (3/3), and in s12 it never raised the typed-amount vs cents conflict (3/3). setup 21/21 vs 14/21: 2.1.2 asked for values the repository shows and did not show where detected values came from. wrap-up 27/27 vs 20/27: doc entries that need the run to be read, unflagged open follow-ups. over-engineering: in o3 2.1.2 did not name the unrequested options (3/3).
- Reviews and checks: 2.1.2's pr-review approved the planted limit bug in 2 of 3 wr3 runs, and its verify-task passed the task with the missing USAGE test in 2 of 3 xl3 runs; 3.0.0 returned the right verdict in all six. 3.0.0 misses the trailing unknown option in xa1 in 1 of 3 runs (PASS where FAIL is right).
- Where 3.0.0 trails: in wr3, lr1 and xl3, six 3.0.0 reviewer runs reported that the CLI accepts unknown flags as a Medium or security defect. They apply 3.0's security standard (`a CLI refuses a flag it doesn't know, in any position`, a hard gate for any change that takes CLI flags), but those scenarios' ground truth predates the rule and says nothing else is wrong, so the judges counted false positives (wr3.no_false_positive 2/3, lr1.no_false_positive 2/3, xl3.no_false_defects 2/3 failed); in one xl3 run the flag finding took the place of the real gap. 2.1.2 raised no such finding. This is the round's open question for the maintainer: narrow the standard's CLI-flag check, or keep it and update those scenarios' ground truth.
- Process: 108/111 vs 55/111. Most process points are 3.0 mechanics that 2.1.2 was never written for - SIMPLE work done inline after one approval (s11 and s11r: 2.1.2 fails level, approval count, inline and subagent checks 3/3), the probe rules (xs2 0/9, xl3 probing 0/3), the CLAUDE.md routing block in setup. The gap shows that 3.0.0 follows its own workflow, not that 2.1.2 does the work worse; the outcome numbers carry that comparison.
- Cost: 3.0.0 uses 30% fewer tokens per run (1,000,616 vs 1,424,158 mean) and less time on average (167.7 vs 240.0 s; medians 131.2 vs 130.4 s). The saving sits in the main-thread planning flows - plan-simple 1,870,863 vs 4,821,014 tokens and 285.4 vs 688.4 s, plan-standard 1,206,000 vs 2,467,299 tokens, address-feedback 1,772,582 vs 3,045,382 tokens. debug costs more in 3.0.0 (2,738,257 vs 1,666,026 tokens, 443.4 vs 239.7 s) for 23/24 vs 21/24 outcome. Worker scenarios cost about the same.
- Same in both arms: q1's mutant M10 (the refunded fee floored instead of rounded half-up) survives every run's tests in both arms (39/42 each); o1, wv3, lv1 and ar1 are full marks in both arms.
- Contamination: 68 of 138 runs (40 of 69 for 3.0.0, 28 of 69 for 2.1.2) loaded at least one skill from the Ritus build installed in the same Copilot CLI (a 3.0.0 pre-release from 2026-09-29, which still had model routing) through the CLI's skill tool, instead of reading only their arm's copy - 44 from the run agent itself, 24 only inside subagents it started; the skills were verify-task, pr-review, execute-task, ticket-review and debug. The runtime tells subagents to invoke a matching skill, and that wins over the brief. contamination.py lists the runs; scores.md repeats every table without them. Clean runs (29 for 3.0.0, 41 for 2.1.2): outcome 207/213 (97.2%) vs 221/274 (80.7%), process 28/29 (96.6%) vs 26/53 (49.1%) - the same direction and size as all runs. Per-group clean numbers are thin (plan-simple and address-feedback have no clean runs), so the group tables use all runs.
- Harness changes made during the round (evals/harness): p4 reads PR #12 through a stub helper in both arms (its two first launches ran without it and were discarded and rebuilt); judge.py bundles a round's scenarios under their latest ground truth (the round had first been bundled with an older iteration's judge groups); grade.py's f1.values accepts a runtime profile with no routing setting - 3.0.0 removed model routing and the check failed 3.0.0 in 3/3 runs for that alone (3.0.0's f1 outcome was 18/21 before the fix, 21/21 after); contamination.py is new; scores.py writes the clean tables and the cost of each group.
- Caveats: n = 3 per scenario and arm; prompts and scripted replies in English; executors and judges are gpt-5.5 subagents of Copilot CLI, not Claude; the arms are 2.1.2 at git:fcbd5d5 and the uncommitted 3.0.0 working tree. One 2.1.2 run (xs2 run 1) includes a 31-minute runtime stall between two tool calls (its model time is 116 s); without that run 2.1.2's mean is 213.8 s. Three runs had a subagent launch refused by the runtime's concurrent-agent limit: s11 3.0.0 run 3, p5 3.0.0 run 2, r1 2.1.2 run 2.
