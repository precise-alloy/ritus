## Notes

- Design: the frontend-compare round (`build.py round --show frontend-compare`, iteration 29): 11 TinyLedger Web scenarios in 7 groups (4 system-level, 3 step probes) x 2 arms x 3 runs = 66 runs, all collected and graded - by scripts, by Playwright and axe measurements of each built app, and by 156 judge verdicts from 3 blind bundles that mix both arms. Each assertion is an outcome (what the developer gets) or a process point (a workflow mechanic). Both arms ran in one dedicated Copilot app session with the Playwright MCP, playwright-cli (Playwright 1.63.0), the Figma stand-in and the figma-design-to-code guidance skill available. The numbers below come from scores.md; the per-run pass rates and medians come from benchmark.json.
- Overall: outcome 205/207 (99.0%) for 1.0.0 vs 191/207 (92.3%) for 0.2.0; process 48/48 (100%) vs 45/48 (93.8%); mean per-run pass rate over all assertions 99.2% vs 92.1%. 1.0.0 is ahead on outcome in 4 of the 7 groups (system-plan, system-gate, system-simple, probe-verify) and level in the other 3 (system-standalone, probe-build, probe-review). Per scenario it trails only in uv2, by 1 assertion.
- Largest outcome gains: system-plan 24/24 vs 18/24 - 0.2.0's up1 plans listed 375, 768 and 1280px but not the 640px and 1024px breakpoints, and left WCAG 2.2 AA contrast out of Acceptance, in all 3 runs (up1.ui_acceptance and up1.a11y 0/3). system-gate 30/30 vs 26/30 - in ug1 runs 1 and 2, 0.2.0 fixed the 375px overflow and the unassociated label without reporting them and first mentioned them at wrap-up (ug1.caught_overflow and ug1.caught_label failed); in run 3 its visual-verify and a11y-verify gates reported both first. 1.0.0 showed the developer Request Changes naming both defects before fixing them, in all 3 runs. probe-verify 56/57 vs 53/57 - in uv5, where the UI is correct, 0.2.0 returned VERIFY: FAIL in runs 1 and 2 on testing grounds alone (regression coverage, UI tests that could not run), with no UI defect (uv5 5/9 vs 9/9). system-simple 26/27 vs 25/27 - the short chat plan named a browser check in Acceptance in 2 of 3 1.0.0 runs and 1 of 3 0.2.0 runs (us1.plan_in_chat).
- Where 1.0.0 trails: uv2, 11/12 vs 12/12. In run 3 its verify-task caught the planted overflow but also blocked on the fee-preview heading's font weight of 700, the browser default for an h2, as not matching a token; the judge counted a false defect. 1.0.0's verify.md says a value the change only reuses is a user note, so this is that rule missed in 1 of 3 runs. 0.2.0 raised no false UI defect in uv1-uv4; its uv5 FAIL verdicts in runs 1 and 2 (above) count as false defects there.
- Process: 48/48 vs 45/48. The whole gap is ur1.used_browser: 0.2.0's pr-review reviewed the code and opened no browser in all 3 runs, and 0.2.0 has no browser instruction at pr-review; 1.0.0 loads the frontend standard into pr-review and audited in a browser (Node Playwright scripts) every time. Both arms requested changes naming the /api/summary 404 and the raw #1F2328 in all 3 runs (ur1 outcome 15/15 each), so the gap measures a 1.0 mechanic, not a worse review verdict.
- Cost: 1.0.0 uses 7% more tokens per run (1,901,422 vs 1,782,166 mean; medians 1,362,762 vs 1,152,717) and 4% more time (295.1 vs 284.6 s; medians 227.0 vs 173.7 s). The extra sits in the step probes where 1.0.0 checks in a browser: probe-verify 1,431,983 vs 1,069,142 tokens (+34%) and 242.6 vs 163.2 s, probe-review 1,101,718 vs 665,076 tokens (+66%) and 165.2 vs 111.3 s, probe-build 1,452,316 vs 1,273,349 tokens (+14%). 1.0.0 costs less in system-plan (1,410,100 vs 2,166,475 tokens, 273.8 vs 431.8 s) and system-standalone (663,524 vs 998,115 tokens, 117.0 vs 121.6 s). system-gate and system-simple cost about the same in tokens (5,242,038 vs 5,197,732; 3,886,031 vs 3,957,367) and less time in 1.0.0 (688.9 vs 816.1 s; 535.5 vs 616.1 s).
- Same in both arms: uc1, the standalone check, is 15/15 in both - FAIL naming the overflow and the label, with no false defect, in every run. ub1 is 39/39 in both: every build matched the Figma node's geometry, colors and type, reused the card component, and passed routes, overflow, axe and console checks; 0.2.0 also added a browser test file in all 3 runs and 1.0.0 added none, which no assertion grades. uv1, uv3 and uv4 are 12/12 in both: every planted defect was named.
- Browser use: in verify and review 1.0.0 mostly used playwright-cli or Node Playwright scripts; 0.2.0 used Node scripts and sometimes the Playwright MCP. In uc1 1.0.0 used playwright-cli, scripts and the MCP across its runs, 0.2.0 mainly the MCP. In ug1 both arms used the MCP and Node scripts.
- Contamination: contamination.py flagged 0 of 66 runs, so there is no clean-runs table in scores.md or RESULTS.md: every table covers all runs. It counted 12 loads of figma-design-to-code, the guidance skill both arms are given (ub1 runs 1-3 in both arms, uv1 1.0.0 runs 1-3 and 0.2.0 run 2, ur1 1.0.0 runs 2-3). Four runs called the host's skill tool for a name that is not installed in the session, and the call failed with nothing loaded: ug1 1.0.0 run 1 (pr-review), ug1 0.2.0 runs 2 and 3 (a11y-verify), us1 0.2.0 run 2 (e2e-plan, a11y-verify, pr-review). No subagent launch was refused.
- Run history: 66 of 66 runs completed. One was relaunched: ub1 0.2.0 run 3 was in flight during an app restart and was cancelled with no report; its one added file was deleted, every built file still matched the build snapshot, and a fresh run replaced it. Every run's timing.json lists gpt-5.5 as its only model, nested subagents included.
- Caveats: n = 3 per scenario and arm; prompts and scripted replies in English; run agents and judges are gpt-5.5, named explicitly on each launch because the host app's default subagent model changed during the 1.0 work. Every harness step of this round ran on Python 3.13.13 (a uv-managed venv); the 3.13.12 to 3.13.13 switch happened during an earlier, unpublished 1.0 iteration round. The 0.2.0 arm pins Ritus 3.0.0 at git:6c03d3a, before D4 - the core change that lets a companion load its standard at task generation and names companion load items for verify-task, pr-review and wrap-up workers - so 0.2.0 has fewer load points by design. Fixture fixes made during the 1.0 iterations apply to both arms here: each world's docs carry its allocated dev port, and the new arm's docs/FRONTEND.md is committed in the world's history. Both arms get the same environment; a benchmark where each arm gets its own recommended environment is not part of this comparison. 1.0 was iterated against a 0.2.0 baseline before this round; those rounds are not published.
